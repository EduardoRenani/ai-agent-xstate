# 007 — Release & Distribution

## Status

Draft. Companion to milestone M4 (`packages/atlas` API complete per specs 004–006). Codifies the rules that turn the in-repo workspace package into an installable npm artefact and a reproducible release process.

## Goal

Ship `packages/atlas` to the public npm registry as an installable package under the name `@eduardorenani/atlasjs`, gated by an automated CI/CD pipeline triggered from GitHub Releases. The contract this spec defines is the **distribution surface** — what the user gets when they run `npm install @eduardorenani/atlasjs` — not the API surface, which is owned by specs 004–006.

Concretely:

- The published package is **`@eduardorenani/atlasjs`** (the bare name `atlas` is taken on npm; `atlas-ts` and `atlas-js` were also taken; the bare `atlasjs` was blocked by npm's similarity policy because it visually collides with `atlas-js`).
- The published artefact is **ESM-only**, with TypeScript declarations (`.d.ts`) generated by `tsc`.
- Source `.ts` files are **not** shipped. The package consumed from the registry must work without TypeScript and without `allowImportingTsExtensions`.
- Pre-1.0 versions publish under the **`alpha`** dist-tag. `npm install @eduardorenani/atlasjs` (no tag) must not resolve to a pre-release.
- Publishing is gated on **GitHub Release publication** of a tag matching `v*`. No `npm publish` from a developer machine in steady-state.

## Problems Addressed

### P1 — Source-as-distribution does not survive npm install

Today `packages/atlas/package.json` declares `main: "src/index.ts"` and `index.ts` imports relative modules with explicit `.ts` extensions (`packages/atlas/src/index.ts:7-33`). The base tsconfig sets `allowImportingTsExtensions: true` and `noEmit: true` (`tsconfig.base.json:10-11`). This works inside the monorepo because `vitest` and `tsx` consume `.ts` directly, but it is **not a distributable shape**:

- Node ESM does not resolve `.ts` extensions.
- A consumer's `tsc` will reject `.ts` import specifiers unless they also opt into `allowImportingTsExtensions`, which is itself only legal with `noEmit`.

The published artefact must be plain `.js` (ESM) with side-by-side `.d.ts`, and its internal relative imports must use `.js`. This requires a build step that rewrites the `.ts` extension to `.js` on emit (TypeScript 5.7+ `rewriteRelativeImportExtensions`).

### P2 — Name collision on `atlas`

`atlas`, `atlas-ts`, and `atlas-js` are all taken on the public npm registry (unrelated projects). The bare `atlasjs` was attempted next but the registry rejected the publish with a 403 citing its similarity-policy block — visually too close to `atlas-js`. The published name is therefore the scoped `@eduardorenani/atlasjs`. The directory `packages/atlas/` is **not** renamed — only the `package.json#name` and any cross-workspace consumers (`examples/zoe`) change.

### P3 — Pre-1.0 versions must not be the default install

The library is alpha. `npm install @eduardorenani/atlasjs` without an explicit version should not pull a pre-release that may change shape. Pre-releases are published under the `alpha` dist-tag, and the `latest` dist-tag is held back until the first stable cut. This is npm's standard pre-release convention; codifying it here prevents accidental promotion of an alpha to `latest`.

### P4 — Ad-hoc local publishes are not reproducible

`npm publish` from a developer machine bypasses CI: there is no guarantee that tests passed, that the build was clean, or that the artefact matches the tagged commit. A consumer cannot audit who published what. The release pipeline runs from GitHub Actions, uses the workflow-issued `NPM_TOKEN`, and emits npm provenance attestations so the public registry can show the source commit and workflow run.

### P5 — No defined release trigger

There is no convention for "this commit is a release". A GitHub Release on a tag `vX.Y.Z` becomes the single signal: creating a release publishes; nothing else does. The Release body holds the human-readable changelog; the tag holds the version.

## Decisions

### D1 — Package name: `@eduardorenani/atlasjs`

User-scoped because every unscoped variant (`atlas`, `atlas-ts`, `atlas-js`, `atlasjs`) is either taken or blocked by npm's similarity policy. Import shape: `import { defineAgent } from "@eduardorenani/atlasjs"`. Scopes are free on the public registry and bypass similarity collisions, so this is the realistic fallback rather than negotiating with the owners of the colliding names. The workspace directory remains `packages/atlas/`. If a future stable cut justifies a shorter bare name, renaming a scoped package is a deprecation/rename event the registry already supports — this decision is reversible.

### D2 — ESM only, no CJS

The package is `"type": "module"` and ships ESM only. Atlas peer-depends on `xstate@^5`, which is itself ESM-first; consumers in CJS environments would already be paying interop tax on xstate. Shipping dual CJS/ESM doubles the build matrix and historically introduces type-resolution edge cases (`exports` conditions, `.d.cts` vs `.d.ts`) that are not worth carrying through an alpha. Revisit at 1.0 if a real consumer requests CJS.

### D3 — Build with `tsc` + `rewriteRelativeImportExtensions`

The build is `tsc -p tsconfig.build.json && node scripts/fix-dts-extensions.mjs`. The build tsconfig sets:

- `module: "nodenext"` / `moduleResolution: "nodenext"` (the published artefact targets Node ESM consumers, not bundlers).
- `outDir: "dist"`
- `rootDir: "src"`
- `noEmit: false`
- `declaration: true`
- `declarationMap: true`
- `sourceMap: true`
- `rewriteRelativeImportExtensions: true`

The last flag rewrites the `./foo.ts` specifiers in source to `./foo.js` in emitted JS (TS 5.7+). This lets the in-repo source stay `.ts`-explicit (so `tsx`, `vitest`, and the IDE keep working today) while the published artefact is valid Node ESM. No bundler is used: the library has no asset graph and no dependencies to inline.

**Known TS 5.9 bug, mitigated**: `rewriteRelativeImportExtensions` does not rewrite extensions inside emitted `.d.ts` files (only emitted `.js`). The post-build script `scripts/fix-dts-extensions.mjs` walks `dist/**/*.d.ts` and rewrites `from "./foo.ts"` → `from "./foo.js"` for relative specifiers only. Drop the script once TypeScript ships the fix.

### D4 — `package.json` distribution fields

The package manifest declares:

- `"main": "./dist/index.js"`
- `"types": "./dist/index.d.ts"`
- `"exports": { ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" } }` — single entry; no deep imports.
- `"files": ["dist", "README.md", "LICENSE"]` — explicit allowlist; nothing else is published.
- `"sideEffects": false` — enables tree-shaking by downstream bundlers; the package only exports pure constructors and types.
- `"publishConfig": { "access": "public", "provenance": true }` — registry-publish-time settings ONLY (npm 11 deprecated `publishConfig.main` / `types` / `exports`, so the same dist fields live at the top level and the workspace builds atlas before any consumer test runs).
- `"repository"`, `"homepage"`, `"bugs"`, `"license": "Apache-2.0"`, `"keywords"`.

`private: true` is removed.

**Consequence for workspace dev**: with `main` pointing at `dist/`, workspace consumers (`examples/zoe`) cannot resolve `@eduardorenani/atlasjs` until `dist/` exists. The root `npm test` and `npm start` scripts build the package first; CI does the same. There is no "run tests against source" shortcut in this repo — the artefact that ships to the registry is the artefact tests run against locally.

### D5 — Pre-release dist-tag policy

While the version matches `^0\.` or contains a pre-release identifier (`-alpha`, `-beta`, `-rc`), publish under `--tag alpha` (or the matching `beta`/`rc`). The release workflow derives the tag from the version: any version containing `-alpha` → `alpha`; any version containing `-beta` → `beta`; any version containing `-rc` → `rc`; otherwise → `latest`. A pre-1.0 stable version (e.g. `0.1.0`) without a pre-release identifier still publishes to `alpha`, because 0.x is by definition unstable.

**First-publish caveat.** npm's registry sets `latest` to the published version on the **very first publish** of a package name, regardless of the `--tag` argument, and refuses `npm dist-tag rm <pkg> latest` (every package must carry a `latest`). The first alpha of `@eduardorenani/atlasjs` (`0.1.0-alpha.0`) therefore landed at both `alpha` and `latest` simultaneously. This is accepted as a one-time deviation rather than worked around with a placeholder `0.0.0` version that would pollute the version list. The intended steady-state behavior — `--tag alpha` does **not** move `latest` — applies to every publish after the first, which is the property the release workflow exercises. The first stable cut (`1.0.0` or first non-pre-release) explicitly publishes to `latest`, replacing the alpha entry.

Consequence: until the first stable release, `npm install @eduardorenani/atlasjs` (no tag) resolves to the pinned alpha. Consumers who want to track `@alpha` explicitly still get the same version today; the explicit form is preferred in docs and the README install line because it survives the 1.0 transition without re-pulling.

### D6 — Release trigger: `release: published`

The release workflow listens for `release: published` (GitHub Release created on a tag matching `v*`). The release workflow:

1. Checks out the tag's commit.
2. Verifies that `packages/atlas/package.json#version` equals the tag minus the `v` prefix. Mismatch → fail.
3. Runs the full test matrix and the build.
4. `npm publish --provenance --tag <derived>` from `packages/atlas/`.

CI (separate workflow) runs on push and PR to `dev`/`main` and does install + typecheck + test + build. CI does not publish. There is exactly one workflow that can publish, exactly one trigger that runs it, and it requires the `NPM_TOKEN` secret to be present in the repo's environment.

### D7 — Workspace dependency on `@eduardorenani/atlasjs` from `examples/zoe`

`examples/zoe/package.json` currently declares `"atlas": "*"`. It becomes `"@eduardorenani/atlasjs": "*"`. npm workspaces resolves `"*"` to the local workspace package by matching the `package.json#name`, so the example continues to consume source-of-truth code, not the registry. Source imports change from `from "atlas"` to `from "@eduardorenani/atlasjs"` wherever they occur in `examples/zoe/src/`.

### D8 — `.npmignore` is not used

Distribution is governed entirely by `files` in `package.json` (D4). `.npmignore` is omitted to keep one allowlist as the single source of truth and avoid the historical foot-gun where `.npmignore` silently overrides `files`.

## Verification

- `npm view @eduardorenani/atlasjs versions` (after first release) lists the alpha version under the `alpha` dist-tag, not `latest`.
- `npm pack --dry-run` from `packages/atlas/` lists only `dist/**`, `README.md`, `LICENSE`, `package.json`. No `src/**`, no `test/**`, no `tsconfig*.json`.
- A fresh `mkdir /tmp/atlas-smoke && cd /tmp/atlas-smoke && npm init -y && npm install @eduardorenani/atlasjs@alpha xstate@5 && node --input-type=module -e 'import { defineMode } from "@eduardorenani/atlasjs"; console.log(typeof defineMode)'` prints `function`.
- `dist/index.js` contains relative imports ending in `.js`, not `.ts`. `dist/index.d.ts` contains relative imports ending in `.js` (TS's convention for declaration files).
- The GitHub Release workflow run for tag `vX.Y.Z` shows a green `npm publish` step and the registry page for `@eduardorenani/atlasjs@X.Y.Z` shows a provenance badge linked to that workflow run.
- `examples/zoe` continues to run via `npm start` against the workspace copy after the rename — no version of `@eduardorenani/atlasjs` is resolved from the registry during development.

## Non-goals

- Dual CJS/ESM publishing (see D2 — revisit at 1.0).
- Multi-package publishing (additional `@eduardorenani/*` packages, releasing `examples/zoe`). `examples/zoe` stays `private: true`.
- Automatic version bumping (changesets, semantic-release). Versions are bumped manually with `npm version` and pushed as tags; the release is created from the tag.
- Publishing the `docs/`, `examples/`, or repo-level READMEs as part of the npm package. The npm `README.md` is the one inside `packages/atlas/`.
